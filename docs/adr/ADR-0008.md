# ADR-0008: Boot, shutdown, and dependency posture

Context: Should application exit on incorrect config and failed database connection, is database failed connection acceptable for running app as unready, or it panic state. How should application treat problems on start. What the maximum time of idle. Application cannot shutdown when Postgres pools is running and HTTP connections is alive.

Decision: `run() error` returns the error to `main`, and then main writes it to stderr, so it can be parsed as error of application. The config error prevent startup loudly, but the unsetted database connection allows to run application in unready state (`/readyz`) and then after successful ping may do self-heal. `HTTP_SHUTDOWN_TIMEOUT` should be under 30s seconds, because K8S kill timer default is 30 seconds, we should keep our less than that. For the shutdown we create a fresh context with timeout, because the application context is dead and we creating a new one for system shutdown. Defer functions putted in order to drain everything properly, first close server and new connections, then close pool. `pool.Close()` runs afterward via defer - requests still hold pool connections during the drain, so the pool must outlive the server

Consequences: A permanently misconfigured dependency (wrong host, bad password) idles silently as unready instead of failing loudly - the price of resilience is a monitoring obligation

At 10x scale: Alert on long unready state.

Status: Accepted
