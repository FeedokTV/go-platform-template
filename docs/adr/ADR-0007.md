# ADR-0007: Env-only config, stdlib over viper/koanf

Context: Choose libraries like viper, koanf or stdlib on env. By twelve-factor app methodology - platform populates the environment (make in dev, K8S or docker in prod, binary never reads the file). Deleting file layers dependency to avoid security problems. 

Decision: The whole config reads environment variables, for the dev env Make fill it.  Typed struct, defaults + env in one Load(), Validate() with errors.Join. Every part of config is divided by parts (App config/DatabaseConfig/HTTPConfig). For database we read parts of DSN and then build DSN string in code via `DatabaseConfig.DSN()` derived via `net/url`, so special-char passwords can survive (see at config tests). Variables are read via helpers builtin on `os.LookupEnv`, because the contract distinguishes unset (apply default, or fail validation if required) from set-to-empty (a deliberate value that reaches validation) - a distinction os.Getenv cannot see. Defaults are applied by the helpers, not by the stdlib. Parsing errors lives in lookup functions, the semantic functions in `Validate()` that returns one error carrying many of errors, so developer can get all errors at once on startup. And .env contract is documented in .env.example. 

Cost: No hot reload, no file-based local overrides; operators must know the env contract. Makefile migrate commands building DSN from many variables inside.

At 10x scale: koanf/viper when files/remote config appear. DB_DSN escape-hatch override alongside koanf

Status: Accepted
